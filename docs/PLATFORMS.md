# Platforms

One code base, every platform SDL3 runs on: the engine calls only SDL3 and the C standard
library, uses SDL's main callbacks (no blocking main loop), reads files through SDL, and ships
shaders precompiled for every GPU backend. **Honest status: only Windows with MinGW-w64 GCC has
ever been built and run.** Everything else below is configured, written down, and untested.

| Platform | Preset | GPU backend | Status |
|---|---|---|---|
| Windows 10/11, MinGW-w64 GCC | `windows-gcc`, `windows-gcc-release` | Direct3D 12, Vulkan | **Tested**: all tests (Debug and release presets), every example, both sample games. Goldens are D3D12; Vulkan screenshots differ by a few edge pixels in 11 of 29 cases (`docs/TESTING.md`) |
| Windows, MSVC | `windows-msvc` | Direct3D 12, Vulkan | **Never built, never run** (no MSVC on the dev machine). The CI workflow has a `windows-msvc` job, but the workflow itself has never run |
| Linux (GCC/Clang) | `linux` | Vulkan | Configured, never built. CI builds it once the workflow runs |
| macOS (Apple Clang) | `macos` | Metal | Configured, never built. **MSL shaders are generated but have never run** |
| iOS | `ios` (Xcode generator) | Metal | Configured, never built; tests off |
| Android | `android` (NDK toolchain) | Vulkan | Configured, never built; tests off; needs SDL's Java glue |
| Consoles | - | the console's native format | Not possible yet: needs an SDL3 port from the platform holder (below) |

Every desktop preset has a `-release` twin (`docs/BUILDING.md`, "Release builds"). The workflow
`.github/workflows/build.yml` builds Windows (MinGW, Debug and release), Windows (MSVC), Linux and
macOS with engine warnings as errors and runs the tests; **it has never run**, so none of those
jobs is known to pass.

## Add-ons

The add-ons (`net`, `tls`, `http`, `websocket`; `docs/agents/addons.md`) are built and their tests
run (loopback only) by CI on Windows with MinGW-w64 GCC and with MSVC, on Linux (Ubuntu 24.04,
GCC) and on macOS (Apple Clang, arm64), with warnings as errors; the release workflow builds them
into all four SDK archives (Windows MSVC and MinGW, Linux x64 on Ubuntu 22.04, macOS arm64) and
builds programs against them. Their sources use no platform headers: sockets come from SDL3_net,
TLS from Mbed TLS.

- **Emscripten: not supported.** SDL3_net builds only a stub there (a browser has no sockets);
  a web build would need the browser's `fetch` / `WebSocket`, which no add-on wraps.
- **iOS and Android:** never built with add-ons (like the rest of those presets: configured,
  untested). SDL3_net and Mbed TLS support both.
- Consoles: SDL3_net needs the platform's socket layer; not tried.

## Common requirements

CMake >= 3.24, Ninja (or Xcode for iOS), a C11 compiler, SDL 3.4. SDL is found with
`find_package(SDL3 CONFIG)` (pass `-DCMAKE_PREFIX_PATH=<prefix>`); otherwise CMake fetches tag
`release-3.4.20` and builds it as part of the project (a few minutes, needs git and network).
Compiled shaders are committed, so no shader tools are needed unless you change a shader
(`docs/BUILDING.md`).

## Windows

MinGW-w64 GCC (tested with GCC 15.2 from scoop/MSYS2):

```sh
cmake --preset windows-gcc -DCMAKE_PREFIX_PATH=<SDL3 prefix>
cmake --build --preset windows-gcc
ctest --preset windows-gcc
build/windows-gcc/sample_projects/star_courier/star_courier.exe --gpu-driver vulkan
```

MSVC (untested): open a "x64 Native Tools" prompt and use the `windows-msvc` preset; warnings
are `/W4`. SDL is linked statically, so the executables need no DLL next to them.

## Linux (untested)

Install a compiler, CMake, Ninja and SDL3's build dependencies (X11/Wayland, ALSA/PulseAudio/
PipeWire and libudev development packages; see SDL's `docs/README-linux.md`), then:

```sh
cmake --preset linux        # builds SDL from source unless CMAKE_PREFIX_PATH points at one
cmake --build --preset linux
ctest --preset linux
```

Vulkan is the GPU backend (SPIR-V shaders). Headless tests need no display.

## macOS (untested)

Xcode command-line tools, CMake and Ninja (Homebrew), then the `macos` preset as above. The
GPU backend is Metal with MSL generated by `spirv-cross --msl --msl-version 20100
--msl-decoration-binding` (entry point `main0`). It follows SDL's documented Metal binding
order, but no Mac has ever run it: expect to debug resource bindings the first time.

## iOS and Android (untested)

- iOS: `cmake --preset ios` produces an Xcode project (tests off). Signing, the app bundle
  (`MACOSX_BUNDLE` on the game's `add_executable`) and copying `data/` into the bundle (the
  samples' post-build copy targets a directory, not a bundle) still have to be added.
- Android: set `ANDROID_NDK`; `cmake --preset android` builds `libbraty.a` and the examples /
  sample games as *executables*, which nothing on Android can load: SDL's `SDLActivity` loads a
  shared library named `main`, so a game needs `add_library(<game> SHARED ...)` under
  `if(ANDROID)` (not done in the samples or the guide). An APK also needs SDL's `android-project`
  Java glue, and assets must be read from
  the APK (SDL's `SDL_IOFromFile` does this for relative paths; the engine currently resolves
  paths against `SDL_GetBasePath`, see "places that would change" below).

## Consoles

What a console port needs, once the platform holder's SDL3 port (with SDL_GPU) exists:

1. **The SDL3 port** for the console (from the platform's developer program; SDL's console
   ports are not public). Build the engine against it with the console toolchain: add a
   configure preset (toolchain file, `BRATY_BUILD_TESTS=OFF` unless the devkit runs them).
2. **A shader format slot.** `br_shader_blob` (`engine/include/braty/br_gpu.h`) has one slot per
   `SDL_GPUShaderFormat`; `BR_SHADER_FORMAT_PRIVATE` (SDL's console format) already exists and
   is tried first at runtime (`engine/src/gpu/br_gpu_pipeline.c`, `br_gpu_shader_get`).
   Add a compile step for the console's shader compiler to `tools/compile_shaders.py` that
   fills `[BR_SHADER_FORMAT_PRIVATE]` in every generated header (the compiler and its output
   stay under NDA, so this usually lives in a private fork of the script), and regenerate.
3. **Storage.** Game data must come from the title container and saves go through user
   storage. Saves already use `SDL_OpenUserStorage` (`br_save_*`); data files are read with
   `SDL_IOFromFile` on paths under the executable directory, which needs to become title storage.
4. **Platform rules** (suspend/resume, user sign-in, save-data size limits, controller
   disconnect prompts). Since the 2026-11-20 review the engine tracks focus, minimise and
   background events: game time and audio pause while inactive (`window.pause_when_inactive`)
   and games get `br_app_on_lifecycle` callbacks (DEACTIVATED, ACTIVATED, LOW_MEMORY,
   TERMINATING); sign-in, size limits and disconnect prompts are still the game's.

The platform-sensitive spots known today (from the 2026-11-20 review; nothing has been ported, so
expect more):

| Place | Why it would change |
|---|---|
| `engine/src/gpu/br_gpu_device.c`, `br_gpu_create` | Requests `SPIRV | DXIL | MSL` from `SDL_CreateGPUDevice`; add `SDL_GPU_SHADERFORMAT_PRIVATE` (one flag). |
| `tools/compile_shaders.py` (+ regenerated `engine/shaders/compiled/*.h`) | Emit the console's format into the PRIVATE slot. |
| `engine/src/core/br_file.c`, `br_file_read_all` / `br_file_write_all` / `br_file_exists` | Use `SDL_OpenTitleStorage` instead of `SDL_IOFromFile` / `SDL_SaveFile` / `SDL_GetPathInfo`. |
| `engine/src/core/br_file.c`, save storage | User storage is opened once (under the org + app identity, `br_engine_set_save_name`) and kept open for the whole session; platforms that commit on close only commit at exit. Writes go to `<path>.tmp` and are renamed over the save. |
| `engine/src/app/br_app.c`, app lifecycle | Handled since the review (pause when inactive, `br_app_on_lifecycle`), but only tested with injected SDL events on desktop; a real suspend / resume on a phone or console has never run. |
| `engine/src/playtest/br_playtest_stdin.c` | C stdio (`--playtest-stdin`); off with `BRATY_PLAYTEST_STDIN=OFF` (default on Android / iOS / Emscripten and in the release presets). |
| `sample_projects/*/CMakeLists.txt`, the guide's step 2 | Games are `add_executable`; Android needs a shared library named `main`, iOS `MACOSX_BUNDLE`. |
| `engine/src/data/br_scene_reload.c`, `br_data_modify_time` | Hot reload polls `SDL_GetPathInfo`; development only, turn it off (`debug.hot_reload`). |
| `engine/src/core/br_file.c`, `br_save_*` | Busy-waits until user storage is ready (`ponytail:`); consoles want an asynchronous ready callback. |
| `engine/src/app/br_engine.c` (asset root) and `engine/src/data/br_game_config.c` (`br_game_config_load`) | Resolve paths against `SDL_GetBasePath()`; on a console this becomes the title-storage root. |
| `engine/src/app/br_app.c`, screenshot writing | Development only (`--screenshot`), uses `SDL_IOFromFile`. |
| `CMakePresets.json`, `CMakeLists.txt` | A preset with the console toolchain; tests/examples off. |

Everything else (windowing, input incl. gamepads and rumble, audio through `SDL_AudioStream`,
threads for background loading through `SDL_Thread`, timing) is SDL already.
